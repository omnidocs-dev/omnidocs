# Structurizr JSON in a Markdown workspace

The viewer can load one Structurizr workspace export inside a fenced `json` block. It normalizes supported views into the shared renderer model without rewriting the source documents. It does not execute DSL, scripts, includes, or derived Mermaid previews.

## Current workspace

`omnidocs.config.json` selects the local document folder. `OMNIDOCS_DIR` overrides it, and `OMNIDOCS_OUTPUT` overrides the portable output path. The portable builder uses `docs/demo` by default. Pass `--include-configured-workspace` to embed the configured documents explicitly.

The supplied folder has an authoritative `architecture-model.md` and an exported `architecture-json.md`. The import uses that existing snapshot. No source file is generated or modified by the viewer.

## Snapshot contract

An optional Markdown wrapper declares the source relationship:

```yaml
format: structurizr-json
model_source: architecture-model.md
source_dsl_sha256: <64-character SHA-256>
```

The `model_source` path resolves relative to the snapshot document, within the imported folder. If either source field is present, both are required. There must be exactly one closed `structurizr` block in the source and one closed JSON block in the declared snapshot. Digest comparison uses the exact UTF-8 block content, including its final newline, without whitespace normalization. If the export includes `structurizr.dsl`, its decoded content must also match the source apart from trailing whitespace removed by the exporter.

A stale snapshot is rejected; browser imports retain the last valid workspace, and packaging fails before writing a replacement HTML file. Regenerate the snapshot using official Structurizr tooling after changing the DSL. Freshness checks are not a substitute for running the official parser/inspections.

An ordinary Markdown `json` block containing a workspace `model` and `views` can also be imported without this wrapper. Its freshness is explicitly marked unverified. Multiple workspace snapshots in one selected folder are rejected.

## Supported mapping

- People, software systems, nested containers, and components.
- System context, container, and component views with explicit scopes, element lists, relationships, and original view keys.
- Stable IDs prefer `doc.id`, then `structurizr.dsl.identifier`, with a namespaced exported-ID fallback. `doc.*` is a source-document convention, not a C4 standard.
- Names, descriptions, technology, tags, relationship directions, and model properties are retained. JSON `description` supplies the relationship label. No business modules are expanded into independent services.
- `doc.relationshipKind: Logical Notification` or its explicit tag is retained as a logical notification, distinct from brokered messaging; `doc.deliveryVia` remains a source property and does not invent a direct transport edge.
- Container/component ownership declared in the model supplies the corresponding C4 system/container boundary; external dependencies stay outside it. This adds visual frames, not synthetic model entities.
- Source notes with a matching `view_key` can supply the view's Markdown documentation. All ordinary Markdown files remain browsable, with local relative links handled inside the document reader.
- Layout is generated by the viewer, with ELK for layered diagrams and a balanced overview for rightward, unframed context views. This is not a reproduction of all Structurizr styles or manual coordinates. Diagram text wraps/clamps for readability, while full descriptions/labels remain available in the inspector, tooltip, and original documents.

### Context overview sides

The scoped system is in the center. People are placed on the left, along with systems that use the scoped system; dependencies are on the right. An incoming `doc.relationshipKind: Usage` relationship identifies a consumer when there is no outgoing Usage relationship to that system. Returned events do not move that consumer to the dependency side. Without Usage metadata, an incoming-only relationship identifies a consumer; ambiguous bidirectional systems use the dependency side.

For ambiguous cases, an element property `omnidocs.contextSide` set to `left` or `right` overrides automatic placement. This is an optional viewer layout hint, not a C4 standard or a change to relationship direction. No entity IDs or business names determine placement. Notifications to people stay directed toward the people on the left.

### Inline expansion and visual roles

Expanded container/component views reuse external entities already visible in ancestor views. Their relationships connect to those existing occurrences, rather than duplicating people and external systems inside the expanded scope. Owned elements remain inside a spaced grid, and the expanded box supplies the generated ownership boundary. Opening the whole level from Layers still shows its complete standalone view.

Connections route through gaps between cards. In dense diagrams, hover or select an arrow to show its label; the complete relationship text remains available in the inspector. Directional particles follow the displayed path. Arrange rebuilds card positions and connection routes.

Element icons, border colors, and footer keys distinguish people, systems, external systems, containers, components, and infrastructure. Declared container technology can provide a cosmetic database, broker, or web application cue; its original C4 kind, tags, technology, and properties remain unchanged. Color on links continues to identify the protocol independently of element colors.

Duplicate IDs, invalid scopes, unknown endpoints, out-of-view relationships, malformed blocks, and unsupported nonempty Structurizr view families produce explicit errors. Deployment/dynamic/filtered/image/custom view families are not silently represented as arbitrary C4 layers.

No component/code/deployment/process view, code mapping, repository, protocol, or project decision is inferred from empty documentation folders or prose.

## Inspection status and loaded data

The logistics export contains 31 elements and 55 relationships. Its context view has 15 elements/16 relationships; its draft container view has 30 elements/39 relationships, including 16 containers. The other documentation sections are placeholders rather than renderable graph definitions.

The Studio preserves that source report in its import-status panel rather than claiming the architecture passed official inspections. This pass verified snapshot freshness and viewer references, not a new official DSL validation run.
